# VJ Live Monitor Acceptance

Updated: 2026-10-20

## Implemented contract

Control > VJ Desk now exposes two continuously refreshed buses instead of a manually refreshed reference image:

- `PREVIEW` renders the current layer source staged with `P`, or the exact clip slot explicitly auditioned with Inspect, the clip context menu, or Shift+1–0.
- `PROGRAM` renders the currently selected video output, including its composition routing, opacity, blackout and projection mapping.
- Smooth requests 320x180 JPEG frames at 30 fps Program and 30 fps staged/active Preview (15 fps passive Preview). Balanced uses 15/15 fps; Low CPU retains 10/5 fps. Each bus has one independent request/decode operation in flight. JPEG is decoded with `createImageBitmap` onto canvas. Monitor-only backpressure protects real output; the persisted quality preference and measurements are documented in [Task 17 acceptance](MONITOR_OUTPUT_FPS_2026-10-19.md).
- The loop stops outside VJ Desk and while the document is hidden. Target changes invalidate stale responses. Backend contention returns an immediate `busy` packet; the UI retains the last good frame and counts busy drops.
- Each successful frame reports sequence, PTS, render time and JPEG encode time in the existing fixed 40-byte `SYLV` v2 header. Tauri returns the packet as a raw `ArrayBuffer`, avoiding JSON number arrays and frontend PNG/data URLs. Footers explicitly label monitor fps; active output readouts separately report successful native presents/SDK sends and estimated missed target slots.
- The backend clamps requests to 640x360 / 230,400 pixels, JPEG quality 40-90 and Program decode budget 1-2. Renderer locks are released before JPEG encoding.

The Preview bus now has an ephemeral transport that is separate from project and Program state:

- Staging is explicit. Selection, queue changes and monitor polling never auto-stage. Legacy `P` starts the current layer source paused at zero or its loop in-point. Clip Inspect, right-click > Audition in Preview and Shift+1–0 stage the selected row’s exact stable slot identity; moving clips start at the slot in-point, or at the exclusive out-point minus one millisecond for reverse playback. An authored zero speed and still images stage paused.
- Play/Pause, millisecond seek, forward/reverse speed up to 4x and Clear update only the Preview transport. Slot audition enforces the clip in/out range for Once, Loop and PingPong; rendered out-points remain exclusive even at a paused terminal position. Zero-speed clips remain paused until speed is changed, and still images remain fixed at zero. A reverse or looping clip without an explicit out-point or known duration is refused.
- For legacy `P` staging, the existing layer `Cut`/`Take` path transfers the staged playhead and speed; it cannot consume a slot audition. For a slot audition, Perform `Take Preview` and its existing Take dispatcher use the ticketed `launch_video_clip_slot_authoritative` path with the accepted layer, slot and Preview generation. This launches the slot from its canonical cue position with its authored speed, launch quantization and configured transition; it does not transfer manual Preview seek/speed changes. Selection or a different queued slot cannot retarget it, an active transition is refused, and a rejected request cannot fall back to another clip. Successful publication clears Preview.
- Preview supports local `File` and `Still Image` sources with a valid path. Camera, Screen, NDI and Spout sources are deliberately rejected so auditioning cannot consume a shared latest-frame queue.
- Preview transport and slot identity are runtime-only: Program, outputs, recording, `.sdc`, Recovery and Undo/Redo never read them. New/load/Undo/standby transitions, layer removal, source identity replacement and Clear invalidate Preview. A staged slot also expires on removal or any change to its authored slot/media identity (including relink, trim, speed and asset hash/size); stable-id reorder, selection, queue and Program playhead changes do not retarget it.
- Preview owns a dedicated decoder/renderer, uses decode prefetch zero and renders a detached one-layer snapshot with the auditioned media plus the layer FX chain. Reset uses `try_lock`; invalidation marks a pending reset before fallible restaging or Take validation, so the next decode cannot reuse an invalid decoder. Source snapshots are captured after acquiring the Preview mutex. Layer, slot and generation are checked after rendering and again after JPEG encoding; a raced frame returns `busy`. The frontend also rejects old generations during asynchronous bitmap decoding.
- **Effect audition (2026-10-19).** `set_vj_preview_effect` attaches an ephemeral layer effect chain to the staged Preview session (`effect_audition`). Only the Preview branch of `render_live_video_monitor_frame` reads it; Program, outputs, recording, projects, Recovery and Undo never do. Restaging another valid slot on the same layer keeps the FX draft; staging another layer, Clear, an invalidated source/slot or a removed layer ends it. Each change advances the transport generation so a frame rendered with the previous chain is reported busy. Applying the FX draft to Program remains a separate, explicit operator action through the ordinary ticketed layer-chain command. Clip Take does not silently persist an FX audition draft. See `qa/FX_UX_2026-10-19.md`.

## Claim boundary and remaining performance work

This closes the independent Preview playhead gap for local files and stills. It does **not** prove that either monitor samples the final native WGPU swapchain: Program is a CPU render from the same project state and mapping rules, Preview is a separate CPU render of the staged layer, and the Display window remains a separate 60 Hz native GPU path. Preview has independent transport time and speed, but it still reads the staged layer's current transform, color and effect definition; it is not a second persisted layer editor. Preview audio scrubbing and live Camera/Screen/NDI/Spout staging are not implemented.

The Program monitor still shares its renderer with existing diagnostic/recording-adjacent preview work and can report visible busy drops under contention. Preview has a dedicated renderer and non-blocking reset, but it also creates a separate decoder session/cache rather than sharing decoded frames with Program or output workers. Real-media sustained fps, freshness, aggregate CPU/GPU cost, cache duplication and native-output interference still require measurement.

The Libav backend now keeps an eight-layer LRU working set, with at most one sequential decode session and one RGBA frame per retained layer. Requests advancing by at most 250 ms continue the same demuxer/decoder; repeated requests reuse the current decoded frame, while reverse motion, loops, larger jumps, source/size/signature changes and errors explicitly reopen or evict the session. Non-file, pathless and HAP-routed replacements release stale sessions immediately. Decoded PTS and seeks share the stream start-time origin instead of assuming zero-based media. Generated MPEG-4 B-frame and offset-start streams are compared against an independent FFmpeg sequential RGBA oracle, including forward continuation, reverse/large-jump reopen, EOF drain and terminal-frame reuse. Session/open/reset/continue/reuse/eviction/error counters are exposed in runtime diagnostics. The CLI fallback is independently capped to a one-frame-per-layer, eight-layer LRU so no-libav and transient-error paths cannot accumulate full RGBA history.

This removes per-frame decoder construction from ordinary forward playback, but the scaler is still created per request and sessions are not shared between Preview, Program and output workers. No claim of lower VJ playback cost than SynapseRack is allowed until representative multi-layer H.264/H.265/ProRes/HAP measurements pass with both monitor buses enabled on the target venue GPU.
