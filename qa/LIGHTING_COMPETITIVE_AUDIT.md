# Lighting Competitive Audit

Updated: 2026-07-14

## Verdict

Syndocal is already a serious unified show-control application, but it is not yet defensible to claim that it exceeds Daslight 5 as a lighting product. It leads in some technical/operational areas—lighting and video in one cue/timeline, open Art-Net/sACN/serial routing, RDM, active/standby recovery, diagnostics and automated reliability evidence—but Daslight 5 currently leads in lighting-specific effect breadth, fixture-catalog maturity, editable Touch surfaces, hardware standalone playback, detachable workspaces and public product maturity.

The official comparison target for this audit is Daslight 5 version 5.0.6.2, listed for Windows and macOS on 2025-09-05. The product page advertises up to 100 universes, 20,000+ fixture profiles, 1,000 banks, seven live FX engine families with unlimited stacking, Super Scene timelines, Live Mixer, custom Touch surfaces, multiple mobile remotes, 3D visualization, detachable dual-monitor windows, hardware standalone playback and password locking.

- <https://www.daslight.com/en/download.htm>
- <https://eu-litterature.n-g.co/Release/daslight_5_manual_en.pdf>

Local visual comparison on 2026-07-13 used the installed Daslight 5 with `Shinkan2026.dvc` loaded in a maximized 1920x1032 window capture. The earlier `Moving Chaser Rnd` screen was a **Dimmer effect**, not evidence of Pan/Tilt, Chaser or Move behavior; that classification is withdrawn. The verified local Position evidence is only the STATIC scene `Moving-Pos > Center-Up (2)`: the scene/group matrix and 2D stage remain visible while a compact editor exposes a 2D Pan/Tilt pad, exact Pan and Tilt percentage readouts, and separate axis faders. This screen demonstrates dense static-position programming, not dynamic Move FX. Syndocal was subsequently rebuilt as a side-by-side, full-screen-first Position console. Automated containment demonstrates density and reachability, but the same-task operator comparison has not been repeated, so no glanceability winner is claimed. Dynamic Move comparison below therefore uses the official manual only.

## Priority implementation gates

1. Sustain 128 distinct universes through the one-hour telemetry budget on a real Art-Net/sACN node and capture packet loss/jitter. Configuration, engine tick and UI containment are complete at 128; external sustained evidence remains.
2. Continue beyond the completed independent Color, Chaser and Move engines and selective Cue Effect recall: add Curve/Value and image/video Mapping runtimes, named racks, multi-select operations and release/venue evidence for practical stacking. Color/Chaser/Move still require physical fixture, timing and mixed-stack acceptance; that is a field-evidence gate, not a shared-runtime gap.
3. Rehearse the completed source-linked Scene Blocks in a representative show: edit source Cues while placed; exercise loops and jumps under internal Timeline Play; separately verify exact-once loop boundaries under authoritative external timecode, where local jumps are intentionally ignored; then cover Undo/Redo, save/reload `.sdc`, and compare operator steps with Daslight Super Scene. Add DOM windowing and a live-tick gate before claiming worst-case 10,000 simultaneously visible blocks. The source-link/loop/jump implementation gap is closed; field workflow and extreme-density evidence remain.
4. Build an editable Touch layout designer with buttons, faders, encoders, color/XY pads, snap/grid, named layouts and multi-client permissions.
5. Expose the existing 3D scene/model/beam engine as a real-time operator visualizer with camera navigation, focus/selection and performance telemetry.
6. Add named detachable workspaces/windows for dual-monitor programming and live operation.
7. Add full/partial operator lock with credential-safe project policy. Treat hardware standalone playback as a separate hardware-product workstream rather than pretending software alone closes it.
8. Build a curated fixture onboarding/catalog experience on top of GDTF Share: search facets, favorites, cached/offline availability, profile health, missing-profile repair and verified common-rig packs.
9. Run same-host cold start, project-open, control-to-DMX, UI input latency, CPU/GPU/memory and 128-universe soak tests. If Daslight can be legally installed on the comparison host, capture the same measurements there.
10. Broaden serial DMX toward the QLC+ device class: build the maintained VID/PID catalog on top of the completed conservative USB identity recommendation, then add Pro Mk2/Ultra Pro dual output, verified device profiles and serial DMX input. Existing ENTTEC Pro-compatible, DMXKing ultraDMX and Open DMX output remains the baseline; see `qa/SERIAL_DMX_COMPATIBILITY.md`.
11. Complete real controller, DMX node, serial interface, fixture rig, projector and operator rehearsal evidence before any superiority language is published.

## Viewport policy

The primary automated browser gate is 1920x1080. This is where information hierarchy, density, stage/editor coexistence and normal show-operation ergonomics are reviewed. The browser harness also runs 1920x1032 as a measured-work-area fixture; that result is not native evidence. Native Windows acceptance is separate: this workstation's 1920x1032 work area produces a 1920x1009 decorated Tauri client while maximized, an exact 1920x1080 client under F11 fullscreen and the same 1920x1009 client after Esc. The 1280x720 and 1366x768 runs remain mandatory containment fallbacks for smaller displays and scaling pressure, but passing them is not a design-quality sign-off; 2048x1152 remains an extended ceiling regression. The complete five-browser-viewport run passed with document/app overflow 0. At 1920x1080 the static Position surface measures 913x317, its pad 289x307 and its tool deck 499 pixels; Position and Movement Limits both fit without inner horizontal overflow, the Position pane needs no vertical scroll, and its three default Favorites remain initially visible.

The independent Move editor passed its stricter five-viewport browser gate with `Move` selected from the production Type control. All five sizes retained zero horizontal overflow and reachable outer-form/point-list endpoints. At the 1920x1080 primary gate the editor measured 1111x582, with a 599-pixel path desk, 586x450 canvas and 510-pixel inspector in two columns; surface/column coverage was 0.998/1.000 and unused right/bottom space was 0/0 pixels. The 1920x1032 measured-work-area browser fixture and 2048x1152 ceiling also remained two-column. The 1366x768 and 1280x720 compact fallbacks intentionally stacked to one column and passed through pane-local scrolling; those compact results remain regression evidence, not the visual sign-off.

Scene Blocks use the same full-screen-first policy. The 1920x1080 primary browser gate and 1920x1032 measured-work-area browser fixture passed with a one-hour/500-placement surface, bounded ruler/zoom/pan/reveal behavior and separate 250-member Lighting/Video overlap clusters. The native QA path separately loaded the Sample through the real Tauri backend, added one linked block and passed maximized/F11/Esc sizing. It does not combine the browser load with a native 500-placement run. Release UI sign-off requires the aggregate `pnpm --dir app run check:release-ui`, which runs both the general full-application viewport suite and the focused timeline viewport suite. The 2048x1152 ceiling and 1366x768/1280x720 fallbacks remain mandatory regressions, but compact stacking cannot substitute for large-window visual review.

## Claim policy

Passing internal unit/UI tests proves implementation quality, not competitive superiority. “Exceeds Daslight 5” requires all applicable gates above, a documented weighted scorecard with no critical losses, and repeatable real-rig evidence. Hardware standalone parity may be declared not applicable only if Syndocal is deliberately positioned as a software-only product; it cannot silently be counted as a win.
